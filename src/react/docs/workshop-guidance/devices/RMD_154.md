# 154: Unattended Remote Assistance

**Implementation Effort:** Medium — the hardest part is governance and support-tool validation, not the toggle itself.

**User Impact:** Medium — unattended support can materially improve operations for kiosks and shared devices, but it also raises privacy and abuse concerns.

## Overview
Unattended remote assistance should be treated as an exception capability for clearly defined device scenarios such as kiosks, lab systems, digital signage, or other non-user-driven endpoints. In a Zero Trust program, unattended access carries more risk than attended support because no user is present to observe or consent to the session. That means the organization should enable it only when the business scenario truly requires it and only with strong identity, role, device, and audit controls.

## Implementation Guidance
- Define which device classes legitimately need unattended support and document why attended, user-consented support is insufficient for those cases.
- Validate whether your chosen remote support platform currently supports unattended scenarios for the target operating systems and licensing model. Do not assume parity across Windows, mobile, and shared-device scenarios.
- Restrict unattended access to tightly scoped support roles protected by MFA, privileged access approval where appropriate, and audit review.
- Require logging, session history, and any approved recording or transcript capability your compliance program expects, especially for high-value devices.
- Document privacy, labor, and legal considerations before enabling unattended access on user-assigned devices, because local requirements may limit when silent access is acceptable.
- Review usage periodically and remove the capability from device groups that no longer need it.
