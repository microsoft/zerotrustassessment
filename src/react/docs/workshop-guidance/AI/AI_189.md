# Verify agent identity attribution and downstream control eligibility

**Implementation Effort:** Medium - Requires matching source, registry and identity records, then checking authentication evidence for each selected integration.
**User Impact:** Low - Uses read-only checks and an approved benign interaction. It does not enable policies or migrate identities.

## Overview

Finding an agent in a registry does not prove which identity it uses to access resources or which security controls apply. An agent may use a native Entra agent identity, an agent user account, a human user's delegated access or a source-platform identity. Treating these as interchangeable can create false confidence that an agent is protected.

For each representative integration, match the source agent to its registry record using documented identifiers and source-owner confirmation. Record the platform and observation time. A matching display name is not enough. Where an Entra agent identity exists, check its object ID and blueprint relationship. An optional agent user account has a separate ID; detected or Virtual identifiers are not proof of native authentication.

Use an approved benign operation and inspect the corresponding sign-in and resource-access evidence. Determine which principal actually accessed the resource and record agent subject or actor context only where the supported records expose it. Different authentication paths can have different applicable controls. Read access is needed in each relevant source platform and portal; one reader role does not grant access to every system.

Keep a capability record for the integration: matched identifiers, actual authentication principal, supported access and governance controls, evidence gaps and an accountable owner. Mark each intended capability **verified**, **not supported**, **not verified** or **pending**. Decisions must be specific to the platform, operating system and authentication path. Do not retain raw tokens, credentials or sensitive prompt content as workshop evidence.

Inventory-only integrations remain valid discovery outcomes. Registry synchronization does not automatically provide native identity or code-level integration, and SDK adoption is not a universal prerequisite for registry sync. Investigate missing links through the documented platform integration path rather than creating a replacement identity or inventing a detected-identity setup procedure.

This supports *Verify explicitly* by confirming the identity behind resource access before selecting controls, and *Use least privilege access* by matching controls to the actual authentication path. It provides an evidence-based handoff from discovery to policy deployment. Eligibility verification is not proof that a policy has been enforced; ongoing monitoring and enforcement tests are separate activities.
